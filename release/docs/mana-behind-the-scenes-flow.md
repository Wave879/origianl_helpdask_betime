# MANA Behind-the-Scenes Flow

วันที่จัดทำ: 2026-06-09

เอกสารนี้สรุป flow เบื้องหลังของ MANA ในหน้า Help Desk V3 เพื่อใช้จับ flow ใหม่ให้ตอบไม่วน ไม่กว้าง และไม่ทำให้ผู้ใช้สับสน

## ภาพรวมปัจจุบัน

MANA ในหน้าวิเคราะห์ไม่ได้ตอบจากข้อความแชทอย่างเดียว ระบบส่งข้อมูลหลายส่วนเข้า `/api/ai/chat` แล้วให้ backend รวม prompt ก่อนเรียก Azure OpenAI

ทางเดินหลัก:

1. ผู้ใช้กรอกข้อมูลหน้าแรก 6 หัวข้อ
2. หน้า Analysis แปลงข้อมูลเป็น ticket context
3. ผู้ใช้กดปุ่มแนะนำ หรือพิมพ์ถาม MANA
4. frontend ส่ง `ticketContext` และประวัติแชทล่าสุดเข้า `/api/ai/chat`
5. backend ค้น knowledge และ ticket เก่าที่เกี่ยวข้อง
6. backend รวม system prompt, playbook, ticket context, knowledge, ticket history
7. Azure OpenAI สร้างคำตอบ
8. backend มี guardrail/rewrite อีกชั้นก่อนส่งกลับหน้าเว็บ
9. frontend แสดงคำตอบในกล่อง MANA และบันทึก chat history

## ข้อมูลที่ MANA ได้รับ

MANA จะเห็นข้อมูลประมาณนี้:

- ข้อมูล ticket ปัจจุบัน เช่น หัวข้อ, ผู้แจ้ง, เวลา, Area, รายละเอียดปัญหา
- ประเภทปัญหาที่ระบบวิเคราะห์ เช่น Human error, System Bug, Software
- สาเหตุ/วิธีแก้/คำถามเพิ่มจากผลวิเคราะห์
- ข้อความแชทล่าสุดของผู้ใช้
- ประวัติแชทล่าสุด จำกัดเฉพาะช่วงท้าย
- knowledge articles ที่ค้นเจอจากคำใน ticket
- ticket เก่าที่ค้นเจอจาก `helpdesk_tickets`
- playbook ตามประเภทปัญหา

จุดสำคัญ: ตอนนี้ MANA เห็น “บริบทเยอะ” แต่ยังไม่มีสถานะชัดว่าผู้ใช้กำลังถามเรื่องไหนใน flow จึงมีโอกาสตอบซ้ำหรือกว้างเกินไป

## Prompt หลักที่ใช้อยู่

Backend ใช้ไฟล์และกฎหลักเหล่านี้:

- `deploy/pages_bundle/prompts/helpdesk/classify-problem-type.system.md`
- `deploy/pages_bundle/prompts/helpdesk/classify-problem-type.examples.md`
- `deploy/pages_bundle/prompts/helpdesk/classify-problem-type.usecases.md`
- `deploy/pages_bundle/prompts/helpdesk/project-playbooks.md`
- กฎใน `src/routes/ai-chat.js`

กฎตอบแชทหลักตอนนี้:

- ตอบภาษาไทยสั้น 1-2 ประโยค
- ถ้าถามวิธีแก้ ต้องให้ action แรกก่อน แล้วค่อยถามข้อมูลเพิ่ม
- ถ้าเป็น Human error ให้บอกว่าส่ง back office/admin ได้ ถ้าไม่มี bug ระบบ
- ถ้าเป็น Data Issue ให้ขอ record, field, ค่าที่เห็น, ค่าที่ควรเป็น, screenshot
- ห้ามเดา project/team/owner ถ้าไม่มีข้อมูล
- ห้ามตอบ technical ภายใน เช่น table/config/log เว้นแต่ผู้ใช้ถามหรือมีหลักฐาน

## จุดที่ทำให้ MANA ตอบงง

จากรูปที่ผู้ใช้ส่งมา MANA ตอบซ้ำแนวนี้:

> เบื้องต้นให้เทียบข้อมูลในหน้าจอกับ record ที่คาดหวังก่อนครับ ถ้ายังไม่ตรงให้ส่งเลขที่เอกสารหรือ screenshot จุดที่ข้อมูลไม่ตรงมาเพื่อช่วยไล่ต่อครับ

สาเหตุหลัก:

1. Intent หลายแบบถูกตีความเป็นกลุ่มเดียวกัน

คำถามเหล่านี้ควรได้คำตอบต่างกัน แต่ตอนนี้มีโอกาสลงท้ายเหมือนกัน:

- “มีวิธีแก้เบื้องต้นยังไงบ้าง”
- “ขั้นตอนถัดไปที่ควรทำคืออะไร”
- “ต้องเอาข้อมูลตรงไหนเพิ่มอีก”
- “ตอบลูกค้าว่ายังไง”
- “ส่ง Dev ได้ไหม”

2. Repeat guard ยังเป็นแบบกว้าง

ระบบมี guard กันตอบซ้ำ แต่ยังไม่ได้จำแนกว่าเคยตอบ “ขอ screenshot” ไปแล้ว และรอบต่อไปควรเปลี่ยนเป็น “ขั้นตอนตัดสินใจ” หรือ “ข้อความตอบลูกค้า”

3. Prompt สั่งให้สั้นมาก

การบังคับตอบ 1-2 ประโยคดีสำหรับ chat แต่เมื่อผู้ใช้ถาม “ขั้นตอนถัดไป” คำตอบสั้นเกินไปจนเหลือแค่ประโยคเดิม

4. คำว่า Data Issue/record/screenshot มีน้ำหนักสูง

เมื่อ ticket มีคำแนวข้อมูลไม่ตรง, record, screenshot ระบบจะดึงกลับไปคำตอบสูตร Data Issue บ่อย แม้ผู้ใช้ถามเรื่องอื่นแล้ว

## Flow ใหม่ที่ควรใช้

ควรให้ MANA มี conversation state ก่อนตอบทุกครั้ง

```text
รับข้อความผู้ใช้
  -> ตรวจ intent ล่าสุด
  -> ตรวจประเภทปัญหา
  -> ตรวจว่ามีข้อมูลครบหรือยัง
  -> เลือก response mode
  -> ตอบตาม template ของ mode นั้น
  -> บันทึกว่ารอบนี้ตอบเรื่องอะไรไปแล้ว
```

## Intent ที่ควรแยก

### 1. ขอวิธีแก้เบื้องต้น

ตัวอย่างคำถาม:

- มีวิธีแก้ไขเบื้องต้นยังไงบ้าง
- แก้เองได้ไหม
- ต้องลองอะไรดูก่อน

คำตอบควรเป็น:

```text
ลองตรวจรายการเดิมเทียบกับเลขอ้างอิงก่อนครับ ถ้าเป็นการลงผิดให้ส่ง record/เลขเอกสารและค่าที่ต้องแก้ให้ back office/admin ปรับรายการเดิมก่อน
```

ห้ามตอบแค่:

```text
รบกวนส่ง screenshot เพิ่มครับ
```

### 2. ถามข้อมูลที่ต้องขอเพิ่ม

ตัวอย่างคำถาม:

- ต้องเอาข้อมูลตรงไหนเพิ่มอีก
- ต้องขออะไรจากลูกค้า
- ข้อมูลที่ต้องใช้มีอะไรบ้าง

คำตอบควรเป็น:

```text
ขอ 5 อย่างครับ: หน้าจอ/เมนูที่เจอปัญหา, เลข record หรือเลขเอกสาร, ค่าที่เห็นตอนนี้, ค่าที่ถูกต้องที่ต้องการ, และ screenshot จุดที่ไม่ตรง
```

### 3. ถามขั้นตอนถัดไป

ตัวอย่างคำถาม:

- ขั้นตอนถัดไปที่ควรทำคืออะไร
- ต่อไปต้องทำอะไร
- next step คืออะไร

คำตอบควรเป็น:

```text
ขั้นต่อไปให้ยืนยัน record และค่าที่ต้องแก้ก่อนครับ ถ้าพบว่าเป็นผู้ใช้ลงผิดให้ส่ง back office/admin แก้รายการเดิม แต่ถ้าระบบดึงค่าถูกแล้วยังแสดงผิดค่อยส่ง Dev พร้อม screenshot
```

### 4. ถามว่าจะส่ง Dev ไหม

ตัวอย่างคำถาม:

- ส่ง Dev ได้ไหม
- ต้องเลือกเดฟไหม
- ควร assign ใคร

คำตอบควรเป็น:

```text
ยังไม่ควรส่ง Dev ถ้ายังเป็นการแก้ข้อมูลจากผู้ใช้ลงผิดครับ ส่ง Dev เมื่อทำซ้ำแล้วพบว่าระบบแสดง/คำนวณ/ดึงข้อมูลผิดเอง พร้อม record, expected, actual และ screenshot
```

### 5. ขอข้อความตอบลูกค้า

ตัวอย่างคำถาม:

- ตอบลูกค้าว่ายังไง
- ช่วยร่างคำตอบ
- แจ้งกลับว่ายังไงดี

คำตอบควรเป็นข้อความพร้อมส่ง:

```text
รับทราบครับ ทีมจะตรวจสอบเลขเอกสาร/record ที่แจ้ง เทียบกับข้อมูลที่ถูกต้อง และประสานผู้ดูแลให้ปรับแก้รายการเดิม หากต้องการข้อมูลเพิ่มจะแจ้งกลับอีกครั้งครับ
```

### 6. ข้อมูลไม่ครบ

ถ้ายังไม่มี record หรือค่าที่ต้องแก้:

```text
ยังขาดเลข record/เลขเอกสารกับค่าที่ต้องการแก้ครับ ส่งสองอย่างนี้มาก่อน แล้วผมจะช่วยสรุปทางแก้ให้ต่อได้เลย
```

## Response Mode ที่ควรเพิ่มในระบบ

ควรเพิ่มตัวแปรภายในประมาณนี้:

```js
responseMode =
  'fix_first' |
  'evidence_request' |
  'next_step' |
  'dev_decision' |
  'customer_reply' |
  'missing_required_fields' |
  'summary'
```

แล้วส่งเข้า backend พร้อม `ticketContext`

ข้อดี:

- ปุ่มแนะนำแต่ละปุ่มจะได้คำตอบไม่ซ้ำ
- MANA ไม่ต้องเดา intent จากข้อความล้วน
- ปรับ prompt ง่ายขึ้น
- กันอาการถาม “ขั้นตอนถัดไป” แต่ตอบเหมือน “ขอข้อมูลเพิ่ม”

## Flow ที่แนะนำสำหรับหน้า Analysis

ปุ่มแนะนำควร map แบบนี้:

| ปุ่ม | responseMode |
| --- | --- |
| มีวิธีแก้ไขเบื้องต้นยังไงบ้าง | `fix_first` |
| ต้องเอาข้อมูลตรงไหนเพิ่มอีก | `evidence_request` |
| ขั้นตอนถัดไปที่ควรทำคืออะไร | `next_step` |
| ส่ง Dev ได้ไหม | `dev_decision` |
| ตอบลูกค้าว่ายังไง | `customer_reply` |
| สรุปเคสนี้ | `summary` |

## กฎเฉพาะ Human Error

ถ้าเป็น Human Error:

1. อย่าส่ง Dev เป็นค่าเริ่มต้น
2. ให้ขอเลข record/เลขเอกสาร
3. ให้ขอ field หรือจุดที่ต้องแก้
4. ให้ขอค่าเดิมและค่าที่ถูกต้อง
5. ให้บอกว่า back office/admin ปรับรายการเดิมได้
6. ส่ง Dev เฉพาะเมื่อระบบทำงานผิดเอง เช่น ดึงข้อมูลถูกแต่แสดงผิด, เลข running ผิด, กดถูกแล้วผลลัพธ์ผิด

## กฎเฉพาะ Data Issue

ถ้าเป็น Data Issue หรือข้อมูลไม่ตรง:

MANA ต้องแยกก่อนว่าเป็น:

- ข้อมูลต้นทางผิด
- mapping ผิด
- master data/config ผิด
- UI แสดงผิด
- user เลือก/กรอกผิด
- logic ระบบผิด

คำตอบไม่ควรหยุดที่ “ส่ง screenshot” แต่ควรบอกว่าต้องเทียบอะไร:

```text
เทียบค่า actual กับ expected ของ record เดียวกันก่อน
```

## กฎกันตอบซ้ำ

ควรจำ last assistant action:

```js
lastAssistantAction =
  'asked_screenshot' |
  'asked_record' |
  'gave_fix' |
  'gave_next_step' |
  'gave_customer_reply' |
  'explained_dev_condition'
```

ถ้ารอบก่อนถาม screenshot แล้ว รอบต่อไปห้ามตอบถาม screenshot ซ้ำอย่างเดียว ต้องขยับเป็น:

- ให้ขั้นตอนตัดสินใจ
- ให้ข้อความตอบลูกค้า
- ให้เงื่อนไขส่ง Dev
- ให้ checklist ข้อมูลที่ต้องครบ

## ตัวอย่าง flow ที่ควรเกิดจากรูป

บริบท:

- ประเภทปัญหา: Human error
- รายละเอียด: แก้เลขทะเบียนรับ/เส้นทางหนังสือ
- ผู้ใช้ถาม: “มีวิธีแก้ไขเบื้องต้นยังไงบ้าง”

คำตอบที่ควรได้:

```text
เบื้องต้นให้ตรวจเลขรับ/เส้นทางหนังสือของรายการเดิมก่อนครับ ถ้าเป็นการรับหรือเลือกผิด ให้ส่งเลขเอกสารกับค่าที่ต้องแก้ให้ back office/admin ปรับรายการเดิมก่อน
```

ผู้ใช้ถามต่อ: “ขั้นตอนถัดไปที่ควรทำคืออะไร”

คำตอบที่ควรได้:

```text
ขั้นต่อไปให้ยืนยันเลขเอกสารและเส้นทางที่ถูกต้องก่อนครับ ถ้าเป็นข้อมูลผู้ใช้ลงผิดให้ admin แก้รายการเดิม แต่ถ้าระบบสร้างเส้นทางผิดเองค่อยส่ง Dev พร้อม screenshot และ expected/actual
```

ผู้ใช้ถามต่อ: “ต้องเอาข้อมูลตรงไหนเพิ่ม”

คำตอบที่ควรได้:

```text
ขอเลขเอกสารหรือ record, เส้นทาง/เลขรับที่เห็นตอนนี้, ค่าที่ถูกต้องที่ต้องการแก้, ชื่อหน้าจอ/เมนู และ screenshot จุดที่ไม่ตรงครับ
```

## สิ่งที่ควรแก้ในโค้ดต่อ

1. เพิ่ม `responseMode` ใน frontend ตอนกดปุ่มแนะนำ
2. ส่ง `responseMode` เข้า `/api/ai/chat`
3. ให้ backend เลือก prompt/guardrail ตาม `responseMode`
4. เพิ่ม memory ว่า MANA ตอบ action แบบไหนไปแล้ว
5. ปรับปุ่มแนะนำให้ไม่ยิงข้อความธรรมดาอย่างเดียว แต่ยิง intent ชัดเจน
6. แยก prompt สำหรับ `customer_reply`, `next_step`, `dev_decision`
7. ลด rewrite ซ้ำที่บังคับกลับไป Data Issue เมื่อผู้ใช้ถามคนละเรื่อง

## สรุป

ตอนนี้ MANA มีข้อมูลพอ แต่ยังขาดตัวคุม flow ว่า “ผู้ใช้ถามอะไรในขั้นตอนนี้” จึงตอบวนหรือคลุมเครือได้ง่าย

ทางแก้ที่ตรงที่สุดคือเพิ่ม `responseMode` และ `lastAssistantAction` เพื่อให้ MANA ตอบตามหน้าที่ของคำถาม ไม่ใช่ตีความทุกอย่างเป็นการขอข้อมูลเพิ่ม
